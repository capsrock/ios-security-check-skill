# どのアプリでも確認する観点（A1〜A7）

アプリが何をするかにかかわらず、すべてのアプリで確認します。スキャンの結果が手元にあれば、どれも短い時間で済みます。

OWASP のテストのページは、`https://mas.owasp.org/MASTG/tests/ios/MASVS-<分類>/MASTG-TEST-<番号>/` の形をしています。

## A1. 通信の保護の設定

App Transport Security は既定で有効で、適切に保護されていない接続を止めます。アプリがこれを弱めるのは、Info.plist に `NSAppTransportSecurity` の辞書を足したときです。

知っておくべき限界があります。Apple の文書によれば、Network フレームワークや CFNetwork のような低い層の通信の仕組みを使った呼び出しには、適用されません。Info.plist がきれいでも、その経路の通信については何も分かりません。

- **見るところ**: すべての Info.plist の `NSAppTransportSecurity`、スキャンが挙げた `http://` の文字列、スキャンが挙げた低い層の通信。
- **問題になる場合**: `NSAllowsArbitraryLoads` が true になっている。または、例外に指定したドメインで、平文の HTTP や低い TLS の版を許している。そのうえで、どちらの場合も、サーバーを直せない理由がどこにも書かれていない。コードの中の `http://` の URL を実際に読み込んでいる場合や、低い層の通信のコードが TLS なしで接続を開く場合も問題です。
- **問題にならない場合**: `NSAppTransportSecurity` のキーが無く、アプリが URL を読み込む標準の仕組みだけを使っている。この場合は既定の保護が効いています。
- **直す方向**: サーバーを直します。それができないときは、例外を必要な1つのドメインに絞ります。Apple は、例外はセキュリティを下げること、一部の例外は App Store への提出時に理由の説明が要ることを書いています。
- **出どころ**: [Preventing Insecure Network Connections](https://developer.apple.com/documentation/security/preventing-insecure-network-connections) · MASTG-TEST-0321, 0322, 0323, 0342（NETWORK）

## A2. アプリに付けた権限

権限（entitlement）は、それぞれ1つの機能を有効にします。どのコードも使っていない権限は、アプリに必要以上のものを与えています。

- **見るところ**: スキャンの結果に出た、すべての `.entitlements` ファイル。キーごとに、それを必要とするコードを探します。
- **問題になる場合**: 機能が有効になっているのに、何も使っていない。iCloud のコンテナ、App Group、関連ドメイン、キーチェーンの共有、プッシュ通知などです。
- **問題にならない場合**: その機能を、アプリ本体ではなく拡張のターゲットが使っている。または、1つのプラットフォームでだけ使っている。報告する前に、すべてのターゲットを確かめます。
- **直す方向**: Xcode の Signing & Capabilities で、その機能を外します。開発者アカウントの App ID も確かめてください。Xcode がそちらの機能まで無効にするかは、このスキルでは確かめていません。
- **出どころ**: MASTG-TEST-0362（PRIVACY）

## A3. 鍵やパスワードの直書き

アプリに組み込んだものは、そのアプリを持っている人なら誰でも読めます。コミットしたものは、履歴に残ります。

**最初に、どちらの種類の鍵かを見分けます。** 鍵には2種類あり、判断のしかたが違います。

- **秘密の鍵**は、アプリにもリポジトリにも入れてはいけません。サーバー側の API キー、個人用のアクセストークン、署名の鍵、パスワードなどです。この観点が扱うのは、こちらです。
- **アプリに入れて配る鍵**は、読める前提で作られています。Firebase の設定、地図の鍵、決済の公開用の鍵、クラッシュ報告の宛先などです。アプリの中に見つかっても、それ自体は問題ではありません。大事なのは、その鍵で何ができるかです。これは C2 で扱います。

鍵の形からは、どちらの種類かは分かりません。Google の API キーは、どれも同じ形をしています。Firebase は「自分の鍵は、バックエンドの資源へのアクセス制御には使われない」としています。一方で Google は、Gemini の鍵について「パスワードのように扱い、アプリに入れてはいけない」としています。スキャンは、Firebase の設定ファイルの外にある Google の鍵をすべて挙げるので、人が判断します。

- **見るところ**: スキャンが挙げた候補。スキャンは、テストのターゲットを含むすべてのテキストファイルを、3つの方法で探します。
  - 形で探す。鍵の形を、そのサービス自身の文書で確かめられたものが対象です。GitHub、GitLab、Slack、AWS、Stripe と、PEM 形式の秘密鍵のブロックです。AWS で形が分かるのはアクセスキー ID で、これは識別子です。秘密のアクセスキーには決まった形が無いので、その近くを探します。Google の API キーは、よく知られた接頭辞で探しています。この接頭辞は、Google の文書では確かめられませんでした。
  - 名前で探す。サービスを問いません。key、secret、token、password といった名前のものに、乱数のように見える値が代入されている箇所です。
  - ファイル名で探す。署名の鍵、SSH の秘密鍵、`.env`、`.netrc` などです。名前だけを挙げ、中身は開きません。

  出力するのは場所と名前だけで、値は出しません。
- **問題になる場合**: 秘密の鍵が、ソースコード、同梱するリソース、git が管理しているファイルのどれかにある。テスト用のデータや README にある場合も同じです。リポジトリに入っていることに変わりはありません。
- **問題にならない場合**: 公開する前提の識別子（バンドル ID、コンテナの ID）、名前に「token」を含むだけの辞書のキー、見本の値、アプリに入れて配る鍵（C2）。
- **スキャンで見えないもの**:
  - 見分けられる形も、手がかりになる名前も無い鍵。
  - 上の一覧に無いサービスの鍵。
  - **git の履歴の中身。** 一度コミットして、あとで消した鍵は、複製されたすべてのリポジトリに残っています。スキャンが挙げるのは、履歴に出てくる鍵らしい「ファイル名」だけです。
- **さらに調べるとき**: リポジトリを公開している、またはこれから公開するときは、専用の検査ツールを使います。数百種類の鍵の形を知っていて、履歴の全体を読みます。入っていれば使います。入っていなければ、報告にそう書き、入れるかどうかは持ち主に決めてもらいます。
  - [gitleaks](https://github.com/gitleaks/gitleaks): 履歴には `gitleaks git --redact .`、今あるファイルには `gitleaks dir --redact .` を使います。`--redact` を付けると、値が出力に出ません。
  - [TruffleHog](https://github.com/trufflesecurity/trufflehog): `trufflehog git file://.` を使います。既定では、見つけた鍵をそれぞれのサービスに対して試します。つまり、鍵がそのサービスへ送られます。これを止めるには `trufflehog git file://. --no-verification` を実行します。このコマンドに `--results=verified,unknown` の絞り込みを足してはいけません。検証をしないと、結果はすべて「未検証」になり、絞り込みが全部を隠してしまいます。
- **直す方向**: 秘密の鍵はサーバーに置き、アプリはサーバーに処理を頼みます。一度コミットした秘密の鍵は漏れたものとして扱い、作り直します。その行を消しても、履歴からは消えません。
- **出どころ**: OWASP Mobile Top 10 2024 の M1 Improper Credential Usage · MASTG-TEST-0214（CRYPTO）。ファイルに保存した鍵を扱い、API キーも含みます。0213 は、コードに書いた暗号の鍵を扱います · [GitHub のトークンの形式](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/about-authentication-to-github) · [Firebase の API キー](https://firebase.google.com/docs/projects/api-keys) · [Gemini の API キー](https://ai.google.dev/gemini-api/docs/api-key)
- **実行していないこと**: これを書いた時点で、どちらの検査ツールも入っていませんでした。コマンドは各ツールの README から引いたもので、実際には動かしていません。

## A4. 開発用の機能

起動引数、環境変数、デバッグ用のメニュー、テスト用の仕掛けは、開発中は便利です。配布するアプリに残ると、誰も点検していない入口になります。

- **見るところ**: スキャンが数えた、`#if DEBUG` の「外」にあるコード。それぞれの場所を読みます。
- **問題になる場合**: 配布するアプリが、起動引数・環境変数・隠しスイッチを受け付けていて、それが利用者にできることを変える。確認を飛ばす、別のサーバーを指す、機能を解放する、テスト用のデータを読み込む、デバッグ用の証明の仕組みを入れる、などです。
- **問題にならない場合**: そのスイッチが変えるのが、音を消す、最初の画面を選ぶ、といった害の無いことだけ。あること自体ではなく、それで何ができるかで判断します。
- **A7 が前提**: `#if DEBUG` がコードを配布版から外すのは、配布用の設定が `DEBUG` を定義していないときだけです。この件数を信じる前に、スキャンの A7 の行を確かめます。
- **直す方向**: `#if DEBUG` で囲むか、消します。
- **出どころ**: OWASP Mobile Top 10 2024 の M8 Security Misconfiguration。配布版で有効なままのデバッグ機能を、設定の誤りに数えています。OWASP の iOS 向けテストには、起動引数や隠しスイッチそのものを扱うテストはありません。

## A5. 使っていない URL スキーム

登録だけして、どこでも受け取っていないスキームは、穴というより、片付けの対象です。開いてもアプリが起動するだけで、値はどのコードにも届きません。外しておく意味は、あとで受け取る処理を足したとき、誰も点検していないスキームをそのまま引き継いでしまうからです。

- **見るところ**: スキャンの URL スキームの行。すべての Info.plist にあるスキームを挙げ、受け取る処理がコードにあるかを示します。
- **報告のしかた**: 脆弱性ではなく、整理として報告します。
- **問題にならない場合**: 受け取る処理がある。その場合は、その処理を B1 で確認します。
- **直す方向**: Info.plist から、その URL の種類を消します。
- **出どころ**: [Defining a custom URL scheme for your app](https://developer.apple.com/documentation/xcode/defining-a-custom-url-scheme-for-your-app)。Apple は、URL スキームを攻撃の入口になりうるものとして説明しています。受け取る処理の無いスキームが値をアプリに運ばない、という点は、このスキル独自の読み方です。

## A6. 古い版を使えなくする手段

この観点が尋ねるのは、具体的な問い1つです。アプリが、古い版には無い保護に頼っているとき、その古い版を使えなくできるか、です。

これが意味を持つのは、サーバーが、新しい版しか送らないものを必須にしようとしているときです。たとえば、正規のアプリであることを示すトークン（B20）です。サーバーを持たないアプリには当てはまりません。

- **見るところ**: スキャンが挙げた、更新を強制するコード。
- **問題になる場合**: そのような依存があるのに、古い版を使い続けるのを止める手段が無い。
- **問題にならない場合**: アプリの版に依存する保護が無い。強制的な更新の仕組みが無いこと自体は、問題ではありません。対応する OS の版が低いことも、問題ではありません。スキャンがこれを報告するのは、ほかの観点がどの OS の版で成り立つ必要があるかを知るためだけです。
- **直す方向**: App Store の更新を強制する API は、システムにありません。そのため、必要なアプリは、自分で管理している場所から最低の版を読み、古いビルドを止めています。その値がどこから来るかを確かめます。CloudKit の公開データベースなら、B19 を確認します。
- **出どころ**: [MASVS-CODE-2](https://mas.owasp.org/MASVS/controls/MASVS-CODE-2/) · MASTG-TEST-0383（CODE）

## A7. Xcode のビルド設定

ビルド設定は、リポジトリのコードが何になるかを決めます。ここで大事なのは2種類です。開発用のコードを配布版に入れてしまう設定と、保護を切る設定です。

- **見るところ**: スキャンの A7 の行。プロジェクトのファイルにあるすべてのビルド設定、ビルド時に走るスクリプト、`.xcconfig` ファイル、共有しているスキームを読みます。
- **問題になる場合**:
  - Debug 以外の設定が `DEBUG` を定義している。`#if DEBUG` で囲んだものがすべて配布され、A4 が意味を持たなくなります。言語の系統ごとに別々に切り替わり、スキャンはどちらを見つけたかを示します。Swift は Active Compilation Conditions と、Other Swift Flags の `-D DEBUG` に従います。C、C++、Objective-C は Preprocessor Macros と、Other C Flags の `-DDEBUG` に従います。`DEBUG=0` としたマクロは数えません。
  - 配布用の設定で、Enable Testability が有効になっている。
  - ビルド時に走るスクリプトが、何かをダウンロードして実行している。
  - 共有しているスキームが、環境変数や起動引数に秘密の値を持っている。共有しているスキームは、プロジェクトと一緒にコミットされます。
  - 共有しているスキームのアーカイブが、配布用ではない設定でビルドする。
- **問題にならない場合**: `DEBUG` を定義し、テスト用の設定を有効にしているのが Debug の設定だけ。Xcode がプロジェクトを作るときの既定の状態です。
- **ほぼ該当しないもの**: スキャンは、参照カウントの自動化、位置に依存しないコード、スタックの保護が切られていないかも示します。Xcode はこれらを有効のままにします。このスキルを作るのに使ったプロジェクトで、これらを変えていたものはありませんでした。OWASP 自身のテストも、Swift だけのアプリではスタックの保護の確認をたいてい省けるとしています。該当したら、設定を変えた人に理由を尋ねます。
- **欠陥ではなく、事情しだいのもの**: スクリプトのサンドボックスを切っている設定。サンドボックスは、ビルド時のスクリプトが、宣言していないファイルに触れるのを止めます。その制限の下では動かないスクリプトもあります。記録だけして、そのスクリプトがプロジェクト自身のもので、外から何も取ってこないなら、先へ進みます。
- **任意の強化。無くても問題ではないもの**: Xcode の Enhanced Security の設定は、ポインタ認証、型つきのアロケータ、強化された C++ 標準ライブラリ、セキュリティ関連のコンパイラの警告を有効にします。その多くは C と C++ のコードに関わります。スキャンは、設定されているかどうかを報告します。
- **ファイルではなく、ビルド設定にある項目**: Info.plist の項目や Mac のサンドボックスの機能は、plist や entitlements のファイルに現れないまま、ビルド設定として指定できます。スキャンは、知っているものを、それぞれが属する観点に振り分けます。ファイルの共有は B9、App Sandbox は B23 です。プロジェクトが Info.plist を生成している場合は、ファイルにあるはずだと思っていた項目が、ほかにビルド設定に無いかを見ます。
- **直す方向**: Debug 以外のすべての設定から `DEBUG` を外します。ビルド時のスクリプトが取ってくるものは、版を固定して検証するか、リポジトリに取り込みます。スキームの秘密の値は、共有しているスキームの外へ移します。
- **出どころ**: [Build settings reference](https://developer.apple.com/documentation/xcode/build-settings-reference) · MASTG-TEST-0228, 0229, 0230（CODE）
