# サーバーと外部のパッケージ（C1〜C3）

スキャンが、サーバー側のプログラム、アプリに入れて配る鍵、外部のパッケージのどれかを見つけたときに確認します。

C1 と C2 は、一般的な対策です。アプリの安全は、通信する相手の安全を超えられないので、入れてあります。Apple の文書と OWASP の iOS 向けテストは、サーバー側のプログラムを扱っていません。C2 が尋ねること、つまりアプリに入れて配る鍵をどう制限するかも、扱っていません。鍵の直書きについての OWASP のテストが尋ねるのは、鍵があるかどうかだけです。

## C1. サーバー側のプログラム

サーバーは、呼び出してきた相手がアプリだと決めつけられません。要求は、誰でも送れます。

- **見るところ**: リポジトリにある関数や窓口のそれぞれ。何を受け取り、それをどう使い、秘密の値をどこから読んでいるか。
- **問題になる場合**:
  - 要求に入っていた値を、型・長さ・形式を確かめずに使っている。
  - 要求に入っていた値が、メールの宛先、サーバーが取りに行く URL、ヘッダーに書き込む内容のどれかを決めている。
  - アプリからだけ呼ばれるはずの窓口が、その証明を必須にしていない（B20）。
  - 実行環境に秘密の値の置き場が用意されているのに、秘密の値を、プログラムと一緒に配置するファイルに置いている。
  - エラーの応答が、内部の情報を明かしている。
- **問題にならない場合**: 要求を決まった形と照らして検証していて、宛先や送り先はサーバー側で固定してあり、秘密の値は実行環境の置き場から読んでいる。
- **直す方向**: 受け取るところで検証します。宛先と送り先は、サーバー側で固定します。秘密の値は、秘密の値の置き場に移します。アプリ専用の窓口には、正規のアプリであることの証明を必須にします。

## C2. アプリに入れて配る鍵

鍵の中には、アプリに入れるためのものがあります。Firebase の設定ファイル、地図の鍵、決済の公開用の鍵、クラッシュ報告の送り先、解析のトークンなどです。アプリを持っている人なら誰でも読めますが、それは設計どおりです。問うべきなのは、鍵がそこにあるかどうかではありません。それを写し取った他人に、何ができるかです。

- **見るところ**: スキャンがこの観点に挙げた鍵。設定ファイル、SDK に渡している鍵、Info.plist にある鍵らしい項目です。それぞれについて、そのサービスがどの種類の鍵だと言っているかを調べます。形では決めません。いちばん分かりやすい例が Google です。Google の API キーはどれも同じ形ですが、Firebase は、自分たちの鍵はバックエンドの資源へのアクセスの制御には使われない、としています。一方、Google の Gemini の文書は、その鍵をパスワードのように扱い、アプリに直書きしないよう書いています。
- **問題になる場合**:
  - その鍵が、実は、サーバーにだけ置くようサービスが求めている秘密の鍵である。この場合は、A3 の問題です。
  - サービスに制限の仕組みがあるのに、何も設定していない。どのアプリがその鍵を使えるか、サービスのどの機能を呼べるか、読み書きではなく読み取りだけにするか、使用量の上限、などです。
  - 1つの鍵をアプリとサーバーで共有していて、どちらにも絞れない。
- **ふつう、リポジトリからは確かめられません。** 制限は、そのサービスの管理画面で設定します。管理画面を見せてもらっていないかぎり、鍵とサービスの名前を1つずつ挙げて、「持ち主が確かめること」として報告します。
- **問題にならない場合**: 鍵がアプリに入れてよい種類で、このアプリと、アプリが使う機能だけに絞ってある。
- **直す方向**: それぞれの鍵を、このアプリと、アプリが必要とする範囲に絞ります。サーバーと共有せず、アプリ専用の鍵を用意します。サービスに使用量の上限があれば、設定します。鍵の先にあるデータを守るのは、サービスのアクセスの規則と、正規のアプリかを確かめる仕組み（B20）です。鍵を隠しておくことではありません。
- **ここで扱わないこと**: 各サービスが、制限を何と呼び、どう設定するか。サービスごとに違い、変わっていきます。そのサービスの、今の文書を読みます。
- **出どころ**: [Firebase の API キー](https://firebase.google.com/docs/projects/api-keys) · [Gemini の API キー](https://ai.google.dev/gemini-api/docs/api-key)。この2つは、鍵の2つの種類を示す例です。この観点のほかの部分は、一般的な対策です。

## C3. 外部のパッケージ

自分で書いていないコードも、自分で書いたコードと同じ権限で動きます。OWASP Mobile Top 10 の 2024 年版は、サプライチェーンのセキュリティを2番目に置いています。

リポジトリを読んで決められることは狭く、この観点は、その範囲にとどめています。

- **見るところ**: スキャンが挙げた、版を固定するファイル（ロックファイル）と、それぞれの依存先の版の指定のしかた。
- **問題になる場合**:
  - ロックファイルをコミットしていない。そのため、リポジトリが変わっていなくても、ビルドが別のコードを取り込みえます。
  - 依存先を、版やリビジョンではなく、ブランチで指定している。
- **問題にならない場合**: 版を固定していて、ロックファイルをコミットしている。
- **ほかの観点で扱うこと**: リポジトリに置いた鍵やトークン（A3）と、コードをダウンロードして実行するビルドのスクリプト（A7）。
- **このスキルがしないこと**: 既知の脆弱性を調べません。パッケージを誰が保守しているかも、評価しません。どちらも、リポジトリには無い情報が要ります。版を固定してコミットしておけば、ロックファイルを読むツールで調べられるようになります。調べていないことを、報告に書きます。
- **直す方向**: ロックファイルをコミットします。版で固定します。
- **出どころ**: [OWASP Mobile Top 10 2024](https://owasp.org/www-project-mobile-top-10/) の M2 Inadequate Supply Chain Security · [MASVS-CODE-3](https://mas.owasp.org/MASVS/controls/MASVS-CODE-3/) と MASTG-TEST-0273, 0275（CODE）。これらは既知の脆弱性についてのもので、このスキルが専用のツールに任せている部分です
